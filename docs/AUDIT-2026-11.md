# Audit: implicit state machines and unenforced invariants

**Date:** 2026-11-09. **Scope:** `src/` (host, webview, shared), the release and data pipelines in `scripts/` and `.github/`, and the benchmarks. **Plan:** [HARDENING-PLAN.md](HARDENING-PLAN.md) turns these findings into prioritized work.

This audit looked for two things:

1. **Implicit state machines.** State that changes over time and decides behaviour, but lives in scattered fields, promises, timers and flags instead of one place that names its states and transitions.
2. **Unenforced invariants.** Facts the extension depends on that nothing checks — a comment, a convention, or the order of two lines is the only guard.

These matter because they fail in the same way. Each is correct when written, and each breaks silently when a later change disturbs an assumption that nothing records.

## How to read the findings

Every finding has an ID (`SM-n` for a state machine, `I-n` for an invariant, `P-n` for performance) and a confidence level:

- **Measured.** A benchmark, profile, probe test or experiment produced the evidence. The numbers come from a Windows machine, Node 26.13 and the full dictionary (470 MB).
- **Confirmed.** Reading the code establishes it without doubt.
- **Not reproduced.** The code allows it, but an experiment could not make it happen.

`file:line` references are to commit `63205145`.

## Summary

The extension is carefully built. Most modules explain why they exist, much of the code records measurements, and many past bugs have regression tests. The defects below are not careless code. Most are **assumptions that were true when written, and that the code cannot notice becoming false.**

The five findings with the most effect on users:

1. **One rolling data release serves every installed version** (I-1). A schema change on `main` replaces `dictionary-latest` at once. Older installs then download a database they refuse to open, and the "update dictionary" prompt replaces a working database with an unreadable one. This has happened before. It will happen again on the next schema change, and the VS Code 1.145 floor makes it more likely, because users on older editors now stay on old extension versions.
2. **The dictionary update reopens the file it is replacing** (SM-4). The update closes the database before a 119 MB download, not before the rename. Any hover or search during the download reopens it, and on Windows the final rename then fails.
3. **The names dictionary downloads on the user's first search** (I-0). The code comments call it "opt-in" and the README says it costs 400 MB "if you use name lookups". In fact every search provisions it: 84 MB to download and 409 MB on disk, for every user.
4. **Crash reports can put the user's account name in a public issue** (I-13). Stacks are sanitized. Error messages and issue titles are not. A probe test showed a Windows path in both the title and the body.
5. **Adding one tag to the search box blocks every extension for 0.3–2 seconds** (P-1). `refineCounts` is synchronous SQLite on the extension host thread. A one-line page-cache setting gives 1.35–1.6× here and about 3× on slow searches. A precomputed table would make it instant, but that needs a schema change, which I-1 blocks.

The audit also found a **release blocker that the previous PR introduced**. It is fixed in [#20](https://github.com/Saeris/vscode-jisho/pull/20): the packager checked for `dict.da`, which Lindera 5.3 renamed, so `main` passed every check but could not be released (I-10).

## 1. Implicit state machines

The navigation stack (`src/webview/machines/navigation.ts`) is the only explicit state machine. It is XState-hosted, well tested, and validates the state it restores. Everything below is implicit.

| ID    | Machine                 | Where                                               | States (as the code implies them)                                   | Main defect                                                           |
| ----- | ----------------------- | --------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| SM-1  | Database handles        | `webviewHost.ts` `#dictionary`, `#names`            | absent → provisioning → opening → open → closing → absent           | Close and reopen race each other; a failed open can erase a newer one |
| SM-2  | Webview connection      | `webviewHost.ts` `#view`, `#ready`, `#queuedPushes` | none → resolved → ready → disposed                                  | The order of dispose and re-resolve is assumed, not checked           |
| SM-3  | Bridge requests         | `bridge.ts` `pending`                               | sent → answered                                                     | No timeout: a lost answer is a spinner forever                        |
| SM-4  | Dictionary update       | `dictionaryUpdate.ts`                               | idle → checking → prompting → closing → downloading → reload prompt | Nothing stops a reopen during the download                            |
| SM-5  | Tokenizer               | `tokenizer.ts` `cached`, `dictPath`                 | unconfigured → building → built, or failed forever                  | A failed build is cached for the whole session                        |
| SM-6  | Decoration pass         | `posDecorations.ts` `#generation`, `#pending`       | idle → debouncing → computing → painted or superseded               | Keyed by document, not editor; a pass cannot be interrupted           |
| SM-7  | Speech                  | `speech.ts` `cachedJa`, `SpeechSequence`            | one shared `speechSynthesis` queue, no owner                        | An interrupted sequence carries on reading                            |
| SM-8  | Stroke playback         | `useStrokeClock.ts`                                 | React state mirrors a Web Animation                                 | Two sources of truth; well tested, so low risk                        |
| SM-9  | Query cache             | `index.tsx`, `queries.ts`                           | idle → fetching → success or error, cached forever                  | Errors stay cached and there is no retry                              |
| SM-10 | Provisioning status     | host only                                           | not provisioned → downloading → ready → failed → updating           | The webview cannot see any of it                                      |
| SM-11 | Startup trace heartbeat | `log.ts` `heartbeat`                                | running from activation to deactivation                             | A diagnostic timer that never stops                                   |

### SM-1 Database handles — Confirmed

`#dict()` and `#namesDict()` cache one promise each, and clear it when opening fails, so a later request retries (`webviewHost.ts:212`). `closeDatabases()` (`:496`) closes both handles for the dictionary update. There are three gaps:

- `closeDatabases` awaits `close()` **before** it clears the cached promise. A request that arrives during the close gets the handle that is closing.
- The failure branch in `#dict()` sets `#dictionary = undefined` without checking which promise it is clearing. If `closeDatabases` and a new open have happened in between, it erases the newer promise.
- A query already running on a handle that `closeDatabases` closes fails partway through.

Each of these is a missing transition guard. With the states named, "closing" would refuse new opens, and the failure branch would clear only its own attempt.

### SM-2 Webview connection — Confirmed (the risk itself is not reproduced)

`resolveWebviewView` sets `#view` and `#ready = false` (`webviewHost.ts:251`), and `onDidDispose` clears them (`:269`). If an old view's dispose event ever arrives after a new view resolves, it clears the **new** view. The code assumes that order. `#queuedPushes` has no limit and is never trimmed if a webview never becomes ready.

### SM-3 Bridge requests — Confirmed; the push race is Not reproduced

`send` (`bridge.ts:137`) stores a resolver per request and never removes it unless an answer arrives. There is no timeout. If an answer is lost, the TanStack query stays pending, and the user sees "Searching…" with no end.

`webviewReady` is posted while `bridge.ts` is first evaluated (`:108`). The host answers by flushing queued pushes. But `App` subscribes to pushes in a passive `useEffect` (`App.tsx:43`), which runs after the first commit. So "Look Up Selection" with a closed panel depends on the host round trip being slower than React's first render. **Four cold launches all passed**, so in practice it is. Nothing guarantees it.

Settings do not have this problem: both settings subscribers register while the modules evaluate, before any message event can run.

### SM-4 Dictionary update — Confirmed

`updateDictionary` (`dictionaryUpdate.ts:120`) calls `closeDatabases()` **before** the download starts (`:154`). The download takes tens of seconds to minutes. During that time, any hover over Japanese text or any search calls `#dict()`, which finds no cached promise and opens `jisho.db` again. When the download finishes, `rename(tempPath, destPath)` (`download.ts:86`) replaces a file that is open. On Windows that fails with EPERM. The code comment at `webviewHost.ts:487` describes exactly this failure as the reason `closeDatabases` exists.

The fix is an explicit "updating" state that refuses to open the database, entered just before the rename and left after it.

Two smaller gaps:

- The webview's query cache keeps results from the old database (SM-9).
- If the user dismisses "Reload the window?", the session continues on the new file with that stale cache.

### SM-5 Tokenizer — Confirmed

`getTokenizer` caches its build promise with `cached ??=` (`tokenizer.ts:99`) and never clears it after a failure. One failed build — for example, a dictionary in the wrong format, which is the Lindera 5.3 failure — disables tokenization until VS Code reloads. That breaks hover, decorations, search lemmas and the editor commands. The database promises clear themselves after a failure; this one does not. The project has four lazy singletons with **three different failure policies** (see I-15).

`configureTokenizer` must run before the first `segment()`. Nothing enforces this. If it ever runs too late, the fallback path is `process.cwd()/assets`, which in production is not the extension's folder. A call after the build is ignored without a warning.

### SM-6 Decoration pass — Measured

The colouring only runs when the opt-in setting `highlighting.enabled` is on.

- **Split view is broken.** `#pending` and `#generation` use the document URI as the key (`posDecorations.ts:245`, `:300`). `extension.ts:214` calls `refreshSoon` for every visible editor, so a second editor on the same document cancels the first one's timer. A probe test with two editors on one document saw **only one repainted**.
- **A pass cannot be interrupted.** The per-line `superseded()` check (`:120`) assumes a keystroke can arrive during a pass. It cannot. With the tokenizer ready, `await segment()` resumes through the microtask queue, and editor events are macrotasks. A probe that reproduced the loop let a "keystroke" timer run only after the whole 100-line pass had finished (200.9 ms against a 200.7 ms pass). The code comment says "a fast typist can supersede this pass several times over" — that is false. A whole viewport pass blocks the extension host (see P-2).
- `refresh` is called with `void` and `computeRanges` has no `try`/`catch`. A tokenizer failure (SM-5) then causes an unhandled rejection on every repaint.

### SM-7 Speech — Confirmed

`speechSynthesis` is one queue for the whole page. Each `SpeechSequence` tracks only its own token. When `speak()` or another sequence calls `synth.cancel()`, the current utterance ends, `#speakOne` resolves, and the interrupted sequence **moves on to its next reading** while still reporting "playing" (`speech.ts:108`).

Separately, `loadVoices` waits at most one second (`:50`). If no voices have loaded by then, `cachedJa` caches `null` for the session, and every play button stays hidden. Voices that arrive later are never noticed.

### SM-9 Query cache — Confirmed

The client uses `staleTime: Infinity` and `retry: false` (`index.tsx:31`), and **nothing in the webview ever invalidates a query**. An error is therefore final for that query key while the view stays mounted. `ErrorState` offers "Report this problem" and nothing else. A user who was offline during the first download, or who hit an update race, must change their query to try again. The error path also sends users to file an issue for problems that a retry would fix.

### SM-10 Provisioning status — Confirmed

The webview does not know whether the dictionary exists, is downloading, has failed or is updating. On first run the panel shows "Searching…" for the whole 119 MB download. The only progress is a VS Code notification. `ErrorResponse` carries only `message: string` (`messages.ts:710`), so the webview cannot tell "offline", "downloading", "wrong schema" and "bug" apart, and cannot offer the right recovery for each.

### SM-11 Startup trace heartbeat — Confirmed

A 250 ms interval samples event-loop lag from activation until deactivation (`log.ts:68`). It continues after its 200-sample buffer is full. The cost is small, but it is speculative work that never ends. The data is useful: `Jisho: Show Startup Trace` can measure the host stalls described in P-2.

## 2. Unenforced invariants

| ID   | Invariant                                                            | Guarded by                                     | Confidence |
| ---- | -------------------------------------------------------------------- | ---------------------------------------------- | ---------- |

| I-1  | The data release can be read by every installed extension version    | Nothing after the extension is published       | Confirmed  |
| I-2  | A schema mismatch leads to a recovery prompt                         | A comment on `SchemaVersionError`              | Confirmed  |
| I-3  | A response has the same `type` as its request                        | A runtime check in the webview only            | Confirmed  |
| I-4  | The prepared-statement cache stays small                             | A comment that cites a rule that was reversed  | Confirmed  |
| I-5  | A query is fast enough to run on the shared host thread              | Nothing, and nothing measured it until now     | Measured   |
| I-6  | The persisted-view list names every `View`                           | A comment ("not a type error")                 | Confirmed  |
| I-7  | Generated files can be regenerated                                   | A comment naming a script that does not exist  | Confirmed  |
| I-8  | The SQL ranking and the JS ranking agree                             | A comment ("must agree")                       | Confirmed  |
| I-9  | The data release matches the schema of the extension being published | `check-data-release.ts` (this one is enforced) | Confirmed  |
| I-10 | The packager checks the files the provisioner writes                 | Nothing — **fixed in #20**                     | Confirmed  |
| I-11 | Every step of a release runs somewhere before release day            | Nothing                                        | Confirmed  |
| I-12 | An editor transform applies to the text it read                      | VS Code's version check (it fails silently)    | Confirmed  |
| I-13 | Crash reports never include the user's paths                         | `sanitizeStack` — for stacks only              | Measured   |
| I-14 | Webview views cannot keep their context when hidden                  | A comment, which is **wrong**                  | Confirmed  |
| I-15 | Lazy singletons share one failure policy                             | Nothing (there are three policies)             | Confirmed  |

### I-0 The names dictionary downloads on first search — Confirmed

`SearchResults` enables `namesQuery` for every non-empty query as soon as the word results arrive (`SearchResults.tsx:108`). The host sends `searchNames` to `#namesDict()`, which calls `ensureNamesDatabase` and downloads the file if it is missing (`ensureDatabase.ts:190`). So **a new user's first search starts an 84 MB download that becomes 409 MB on disk.**

Elsewhere the code treats this as unacceptable. `namesDatabaseExists` says a feature that "triggered a large download just by being computed would be indefensible", and the `#name`/`#place` tags stay hidden until the file exists. The README says names cost "another 400 MB if you use name lookups." Either the behaviour or the documentation must change. **That is a product decision for you;** the plan sets out both options.

### I-1 One rolling data release for every installed version — Confirmed

`dictionary.yml` rebuilds the database when `src/shared/schema.ts` changes on `main`, and replaces the assets of the single `dictionary-latest` release ("not tied to extension releases"). The host requires an exact schema match (`db.ts:95`). The results:

- **Between a schema merge and the next extension release**, new installs of the current Marketplace version download a database that version refuses to open.
- **After the release**, every user who stays on an older version gets an update prompt: "a newer dictionary is available". If they accept, `updateDictionary` replaces their working database with one they cannot read. Nothing checks compatibility before the download or the swap.
- `SCHEMA_FROZEN` is still `false` (`schema.ts:31`), although its own documentation says to set it "as the FINAL step before the first publish", and 0.2.0, 0.3.0 and 0.3.1 are published. The drift guard is off while users are in the field.
- The VS Code floor is now 1.145, so users on older editors stay on 0.3.x for good. They are certain to meet the next schema change.

Two facts decide the fix. **Every published version hardcodes `dictionary-latest`** (`download.ts:15`), so no change to future code can protect users already on 0.2.x or 0.3.x; only what is published to that tag can. And **the published sidecar already names the schema** (`full schema6 2026-08-03 …`), and the update check already downloads it (`fetchRemoteVersion`), so future versions can refuse an incompatible update cheaply.

`check-data-release.ts` (I-9) checks that the data matches the extension **being published**. Nothing checks it against the extensions **already published**. This failure has already happened once: the comment at `dictionary.yml:45` records the release at a schema the extension rejected.

I-1 also **blocks performance work**: the best fix for P-1 is a new precomputed table, and today any schema change breaks every installed client.

### I-2 `SchemaVersionError` has no handler — Confirmed

The class (`db.ts:42`) says it is "typed so the delivery layer can … prompt the user to update". Nothing catches it by type. It crosses the bridge as a plain message: "The database needs to be updated." When the database is **newer** than the code (I-1), that advice is wrong, because the update check finds the versions equal and reports "up to date". The user has no way forward. Meanwhile `#dict()` clears its cache after each failure, so **every keystroke opens the database again** and fails again.

### I-3 Responses are not tied to requests — Confirmed

`Request` and `Response` are two independent unions (`messages.ts:528`, `:777`). The host's `#dispatch` returns `Promise<Response>`, so returning a `GetWordResponse` for a `search` request compiles. The only guard is a runtime check in `bridge.ts:171`. The comment at `webviewHost.ts:426` shows this has gone wrong before. A missing handler **is** a compile error, which is good. A wrong response type is not. Adding one request type touches five files.

### I-4 The statement cache bound depends on a reversed rule — Confirmed

`SqliteStore` caches one prepared statement per SQL text, and says this stays bounded because `IN (…)` lists "are short by design (see CONVENTIONS.md on why `IN (…)` is banned)" (`store.ts:82`). CONVENTIONS.md **reversed** that rule in August and now prefers `IN` for id batches. `refineCounts` builds lists of up to 900 parameters, so one query can add up to 900 cache entries. **Two sources disagree.** CONVENTIONS.md is the newer and the measured one, so `store.ts` needs to change: bound the cache, or round list lengths up to a few sizes.

### I-5 Every query blocks the shared thread — Measured

`node:sqlite` is synchronous. The extension host is one thread that **every installed extension shares**. A slow query is therefore also a stall in every other extension's hovers and completions. Until this audit, no benchmark measured any query. See section 3.

### I-6 The persisted-view list must name every `View` — Confirmed

`hydrateContext` has a hand-written set of view names, and the comment says a missing one "is not a type error" (`navigation.ts:477`). It has gone wrong before: `browse` and `wordList` could not be restored from #54 until 2026-08-06. `satisfies Record<View["name"], true>` turns this into a compile error. `isView` also checks only `name`, so a field renamed in a later build passes the check and renders a broken view.

### I-7 A generated file names a script that does not exist — Confirmed

`patterns.data.ts` says "re-run `scripts/encode-patterns.ts`". That script has never existed (BACKLOG #21). An agent that follows the file's own instructions cannot.

### I-8 Ranking is defined twice — Confirmed

`search.ts:214` sorts in JavaScript to "mirror the SQL's ORDER BY exactly … the two must agree". The same rule is written in two languages.

### I-10 The packager checked a file Lindera no longer ships — Confirmed, fixed in #20

PR #19 updated the provisioner for Lindera 5.3's layout (`dict.da` became `dict.trie`). `package-platforms.ts` still required `dict.da`. Every check passed, and the next release would have failed while packaging. The cause was the dictionary's file list written in two places. #20 moves it into one module and adds a test that runs the packager's own check on every PR.

### I-11 Some release steps run only on release day — Confirmed

The general lesson from I-10. `package-platforms.ts`, `check-data-release.ts`, the `vsce`/`ovsx` arguments in `publish-vsix.ts`, and `bumpy ci release` run only in the Publish job. A mistake in any of them appears for the first time when a release is attempted.

### I-12 Editor transforms fail silently — Confirmed

`transformEditorText` (`editorCommands.ts:52`) reads the text, awaits the tokenizer, then calls `editor.edit` without checking whether the document changed. VS Code rejects an edit whose version no longer matches, so **text is not lost**. But `edit` returns `false`, the code ignores it, and the command does nothing with no message.

### I-13 Crash reports leak paths through messages and titles — Measured

`sanitizeStack` removes home directories from stacks, and it is well tested (`diagnostics.ts:49`). But the issue **title** is built from the raw message (`` `Crash: ${request.message}` `` at `webviewHost.ts:369`; `` `${message} ${detail}` `` at `report.ts:107`), and the body's `error.message` is not sanitized either. Host errors often contain absolute paths, such as Lindera's "Failed to load dictionary from '…'" or a Windows `EBUSY … unlink 'C:\Users\…'`.

A probe test passed a realistic `EBUSY` message through `issueUrl`. **The account name appeared in both the title and the body** of the prefilled public issue. Spec 21's non-crash report, which carries "the error's message", is the main path. The fix belongs in `issueUrl`, the one place every report goes through, so no caller can forget it.

### I-14 A design-shaping comment is wrong — Confirmed

`bridge.ts:33` says a webview view "has no `retainContextWhenHidden`" and that the option "does not exist". It does: `registerWebviewViewProvider(id, provider, { webviewOptions: { retainContextWhenHidden: true } })` (`@types/vscode` 11757). The persistence layer is still worth having, because it survives a VS Code restart. But retaining context would also keep scroll position, the query cache, stroke playback and the caret when the sidebar collapses, at a memory cost. **That trade is your decision.** One constraint: a hidden webview cannot receive messages even with context retained, so `push()` would need to check visibility.

### I-15 Three failure policies for lazy singletons — Confirmed

| Singleton                   | After a failure                    |
| --------------------------- | ---------------------------------- |
| `#dict()`, `#namesDict()`   | Clear the cache, retry next time   |
| Tokenizer, recognizer chunk | Cache the failure forever          |
| `CommentScopes` WASM        | Cache `false` (degrade on purpose) |
| Speech voices               | Cache `null` forever               |

Each was a reasonable choice in its own file. Together they mean the answer to "what happens after X fails once?" differs per feature, and nothing states which policy applies where.

## 3. Performance

### The dictionary — Measured

`bench/dictionary.bench.ts` was added for this audit. No benchmark measured the database before. All of these run **synchronously on the shared extension host thread.**

| Case                                |   Mean ms | What triggers it                 |
| ----------------------------------- | --------: | -------------------------------- |
| search 日本語 / taberu / 食べました |       0.5 | Each committed query             |
| search ねこ                         |       3.5 | Each committed query             |
| search の (single kana)             |      15.7 | A one-character query            |
| search 日 (single kanji)            |      28.0 | Each committed query             |
| resolveByLemma + getWord            |       1.1 | Each prose hover (on by default) |
| refineCounts, no tag                |      0.14 | The tag autocomplete             |
| **refineCounts, #jlpt-n5 applied**  |   **330** | Adding a tag to the search box   |
| **refineCounts, #jlpt-n1 applied**  | **1,539** | Adding a tag to the search box   |
| **refineCounts, #noun applied**     | **1,952** | Adding a tag to the search box   |
| browse #jlpt-n5 / #noun             |  41 / 238 | Opening a category               |
| getKanji 日                         |      16.8 | Opening a kanji                  |

**Where `refineCounts` spends its time (P-1).** A deoptkit profile of the `#noun` case, recording ticks only, put **4.1% in JavaScript**. 55.7% was in `ntdll.dll` (Windows file I/O) and 40.1% in `node.exe` (SQLite, and turning rows into JS objects). 85% of the heaviest frame was `store.all()`, called from `refineCounts` and `idsFor`. **No change to the JavaScript can win more than about 4%.**

Three experiments sized the real options:

| Change                                                           | refineCounts #noun        | Notes                                      |
| ---------------------------------------------------------------- | ------------------------- | ------------------------------------------ |
| `PRAGMA cache_size = -65536` (64 MB page cache)                  | main query 1,130 → 587 ms | One line. `mmap_size` gave the same result |
| …and count in SQL (`COUNT(DISTINCT)` … `GROUP BY`) instead of JS | 1,238 → 544 ms            | Same 191 groups; no rows copied to JS      |
| Precompute counts for each pair of tags at build time            | expected below 1 ms       | 98 × 98 rows; needs a schema change (I-1)  |

**The page cache helps everything slow (P-3).** The same pragma applied to the whole bench:

| Case                      |   Default | 64 MB cache |  Speed-up |
| ------------------------- | --------: | ----------: | --------: |
| search ねこ               |      3.51 |        1.09 |      3.2× |
| search の                 |      15.7 |        5.12 |      3.1× |
| search 日                 |      28.0 |        9.86 |      2.8× |
| getKanji 日               |      16.8 |        5.09 |      3.3× |
| browse #jlpt-n5           |      41.4 |        20.0 |      2.1× |
| refineCounts (with a tag) | 330–1,952 |   205–1,448 | 1.35–1.6× |
| paths below 1 ms          |         — |           — | no change |

The cost is memory: up to 64 MB for each open connection, filled only as pages are read.

### The editor — Measured

**P-2, decoration pass (opt-in).** The tokenizer bench's highlight walk takes 0.68 ms per line of dense prose (141 characters per line on average). A viewport pass covers the visible lines plus 40 above and below, so about 120 lines and **about 80 ms** of blocked host thread — up to the 219 ms the code comment records for denser text. Scrolling refreshes immediately, passes cannot be interrupted (SM-6), and no per-line cache exists, so scrolling back over coloured text tokenizes it again.

**P-4, hover in code comments (opt-in).** Each hover over a comment calls `stackAt`, which tokenizes from line 0 to the hovered line with no cache (`grammar.ts:343`). The code records 0.069 ms per line: about 140 ms per hover at line 2,000. The comment justifies this as a cost "on a debounced path, paid once per pass". That is true for decorations, but the hover takes the same path **without** a debounce.

**The prose hover is cheap.** Tokenizing a sentence takes 0.083 ms, and the database work takes about 1.1 ms.

### JavaScript shape — Measured (deoptkit)

`deoptkit ci` over the four bounded `*.bench.mjs` workloads:

| Workload       | Findings | Notes                                                                                                           |
| -------------- | -------: | --------------------------------------------------------------------------------------------------------------- |
| deinflect      |        0 |                                                                                                                 |
| recognize      |        0 | The work in #15 holds                                                                                           |
| editorCommands |        5 | A megamorphic keyed lookup in `toPartOfSpeech` (`tokenizer.ts:69`); map churn on Lindera's native token objects |
| examples       |        1 | A megamorphic keyed lookup on part-of-speech codes                                                              |

None of these is worth fixing for speed: a sentence tokenizes in 0.083 ms. **The JavaScript is in good shape. The cost is in SQLite and in how often the code calls it.**

The baselines were re-recorded for deoptkit 0.2.0, which identifies an `obj[key]` site by its code position instead of its runtime key. The old baselines reported the same sites as both "new" and "no longer occurring". All four workloads matched on a second run.

### What the tooling taught us

- **The Vitest preset with every category on cannot profile this repo's heavy cases.** Tinybench runs each case for a fixed time, and logging every inline-cache event wrote 8.4 GB for `refineCounts` and 6 GB for the JS benches. `DEOPTKIT_CATEGORIES=deopts,profile,sources` keeps the ticks and drops the flood.
- **The `*.bench.mjs` files exist for a reason that was not written down:** `observed()` runs a fixed number of iterations, so logs stay small. They can merge into the Vitest benches only when profile mode also limits iterations.

## 4. Documentation that is stale or wrong

Agents read comments as fact. The code has a 27% comment ratio, and most comments explain **why**, which is valuable. These were wrong:

| Where                                       | Claim                                                      | Fact                                                         |
| ------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| `tokenizer.ts:127`                          | Cold build is 192 ms (WASM)                                | ~27 ms with the native binding (`webviewHost.ts:261`)        |
| `store.ts:82`                               | `IN (…)` is banned (cites CONVENTIONS)                     | CONVENTIONS reversed this; `IN` is preferred                 |
| `posDecorations.ts:118`                     | "a fast typist can supersede this pass several times over" | Measured: a pass cannot be interrupted                       |

## 5. What is in good shape

These deserve to be kept, and the plan builds on them:

- **Navigation persistence** checks the state it restores instead of trusting it, and it has a tested fallback.
- **The database is opened read-only**, and handles are closed with `using`. Both are documented, and both reasons are real.
- **The stack sanitizer** is tested against real captured stacks. The leak in I-13 is around it, not in it.
- **The recognizer** has no deoptkit findings after #15.
- **Packaging checks its own output.** `packaging.spec.ts` reads the real bundle for missing externals, and since #20 it also checks the dictionary.
- **The prose hover** is fast, POS-aware and cheap.
- **Comments record measurements**, which made this audit possible. The fix for the stale ones is to keep that habit and connect the numbers to benchmarks that can check them.
