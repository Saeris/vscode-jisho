Every screenshot in the README is **generated by a Playwright scenario**, never taken by hand. The scenarios live in `e2e/docs/` and drive a real VS Code with the extension loaded, the same harness the E2E suite uses.

This buys two things: the images are reproducible, and each scenario **asserts the flow before capturing it** — so a UI change that breaks a documented flow fails the run rather than silently producing a picture of a broken state.

## Running it

```bash
vp run docs:shots
```

Writes light and dark PNGs into `docs/images/`. It is **excluded from the default E2E run** (`vp run e2e`) because it is slow — dual-theme captures across many scenarios — and the main suite's value is being fast enough to run constantly.

The cost of that exclusion: **drift does not announce itself.** Run `docs:shots` whenever a change touches a documented screen. When in doubt, run it; a wrong screenshot in the listing is worse than a slow command.

## When to regenerate

- Any change to the sidebar's layout, the search view, a detail page, or the tab bar.
- Any change to theme colours, spacing or typography.
- Any change to text that appears in a captured screen — a heading, a label, a button.
- After changing a fixture in `e2e/docs/fixtures/`.

If `docs:shots` fails, **the documentation is wrong, not the script.** Read the failure: it is telling you a flow the README describes no longer works that way.

## Adding a screenshot

1. Add a scenario to the appropriate file in `e2e/docs/`.
2. **Assert the state first.** Wait for the specific element the screenshot is about, and assert whatever makes the shot meaningful (a count, a label, a heading). The assertion is what makes this a drift alarm rather than a screenshot script.
3. Capture both themes with the shared helper. Name the pair `<scenario>-light.png` / `<scenario>-dark.png`.
4. **Crop tight** to the relevant UI. Use the region helpers rather than a full-window screenshot — a full window buries the subject in VS Code chrome.
5. Run `vp run docs:shots`, then **look at both PNGs** before embedding them.
6. Embed with the `<picture>` block from the `writing-docs` skill. The `<img>` must be the **light** image.

## Choosing what is on screen

The editor content should model **a task a reader might plausibly be doing**, so the feature's value is legible from the scenario rather than only from the prose. Fixtures live in `e2e/docs/fixtures/`, each recorded in that directory's README with its source and licence.

Match the fixture to the feature:

- Reading or editing Japanese prose → the Guide to Japanese excerpt.
- Hover, part-of-speech highlighting → the mixed-language source file, which is the extension's home turf.
- Reading technical documentation in Japanese → the translated-docs excerpt.
- A feature needing a specific construction (a particular conjugation, a name, a slang term) → original content written for it.

**Any new fixture taken from an external source needs its licence recorded** in `e2e/docs/fixtures/README.md` before it is committed.

## Constraints worth knowing

- **PNG only.** SVG is prohibited in a Marketplace README.
- The captures are **committed**. They are the only way the Marketplace can serve them, since it renders relative paths against the GitHub repo.
- Themes are switched by rewriting the profile's `settings.json` (`setTheme` in `e2e/launch.ts`), not by driving the theme picker — the picker races quick-input focus.
- The harness shares one VS Code across a run, so a scenario must **leave the panel where it found it** or reset at its start. `returnToSearch` handles the common case.
